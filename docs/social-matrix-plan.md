# 社媒矩阵（多账号聚合管理）方案草案

> 状态：**待讨论**，只是方案，代码还没开始写。本文是讨论稿，有几处需要你拍板（见文末「待确认」）。
> 起草时间：2026-11-14

## 1. 要解决的问题

外贸团队通常一个人手上有好几个 LinkedIn / Facebook / Instagram / TikTok 账号（个人号 + 公司主页 + 小号），甚至一个公司有几十个号。现在的痛点：

1. **登录环境混乱**：同一台电脑、同一个 IP 登多个号，平台会判定关联，轻则限流，重则一起封。
2. **账号散在各人手里**：员工离职账号带走；主管看不到谁在发什么、回了谁。
3. **社媒消息和 CRM 断开**：客户在 LinkedIn / Messenger 里聊的事，CRM 里看不到，跟进记录断档。
4. **客户社媒动态看不到**：本期已经做了公开渠道的跟踪（YouTube 订阅源、主页资料变化），但 LinkedIn / Instagram 这类**要登录才能看**的平台，只能靠真实账号环境。

所以「社媒矩阵」本质是：**给每个社媒账号一个独立、稳定、像真人一样的浏览器环境（指纹 + IP），由 CRM 统一分配、审计，并把消息 / 动态回流到 CRM。**

## 2. 总体架构

```
┌──────────────────────────── CRM（现有 Next.js + PostgreSQL） ───────────────────────────┐
│ 社媒矩阵模块：账号库 · 环境配置 · 代理 IP 池 · 分配/权限 · 操作审计 · 消息/动态回流    │
└───────────────┬──────────────────────────────────────────────┬──────────────────────────┘
                │ 环境配置下发 / 启动指令（WebSocket）          │ 回流：消息、动态、发帖结果
┌───────────────▼───────────────┐                  ┌───────────▼───────────────────────────┐
│ 方案 A：员工电脑上的桌面客户端 │                  │ 方案 B：云端浏览器（服务器上跑）       │
│ Electron/Tauri + Chromium 内核 │                  │ 容器里跑带指纹的 Chromium，网页里远程看│
│ 每个账号一个独立 Profile        │                  │ 用于定时抓客户动态、无人值守任务       │
└───────────────┬───────────────┘                  └───────────┬───────────────────────────┘
                │                                              │
         ┌──────▼──────────────────────────────────────────────▼──────┐
         │ 代理 IP 层：每个账号绑定一个固定出口（住宅 / ISP 静态 IP） │
         └─────────────────────────────────────────────────────────────┘
```

建议 **A 为主、B 为辅**：

- 员工日常登录、发帖、回消息 → 方案 A（本机客户端，操作流畅，验证码 / 二次验证人在现场处理）。
- 客户动态抓取、定时检查 → 方案 B（云端，不占员工电脑；只读，不做高风险动作）。

## 3. 三条实现路线对比

| 路线 | 做法 | 优点 | 缺点 | 估算 |
|---|---|---|---|---|
| **① 对接现成指纹浏览器**（推荐先走） | 接 AdsPower / 比特浏览器 / Multilogin / GoLogin 的本地 API：CRM 里建环境、分配给员工，员工本机装对方客户端 | 最快上线；指纹对抗由专业厂商持续维护；风控效果最好 | 每个环境要付对方订阅费；依赖第三方；员工要装两个软件 | 3～4 周 |
| **② 自研桌面客户端** | Electron（或 Tauri）+ 定制 Chromium，自己做 Profile 隔离和指纹参数注入 | 体验统一（CRM 和浏览器一个软件）；无第三方费用 | 指纹对抗是长期攻防，需要专人维护；Chromium 跟版本成本高 | 2～3 个月起，之后持续投入 |
| **③ 云端浏览器** | 服务器 / 容器里跑 Playwright + 指纹插件（如 Camoufox / 定制 Chromium），网页里用 WebRTC/VNC 远程操作 | 员工不用装软件，手机也能用；环境集中在服务器，离职带不走 | 服务器成本高（每个活跃环境约 0.5～1 核 1～2GB 内存）；远程操作有延迟；数据中心 IP 必须配住宅代理 | 1.5～2 个月 |

**建议：第一阶段用 ①（接入一个指纹浏览器厂商 API）把账号管理、分配、IP 绑定、审计跑通；第二阶段用 ③ 做无人值守的「客户动态抓取」；② 等用户规模大到第三方费用压力明显时再评估。**

## 4. 指纹封装（浏览器环境）要隔离什么

每个社媒账号 = 一个独立环境（Profile），以下全部按环境隔离、并且长期固定不变：

| 类别 | 内容 |
|---|---|
| 存储 | Cookie、LocalStorage、IndexedDB、Cache、Service Worker、登录态 |
| 基础指纹 | User-Agent（与内核版本一致）、平台、语言、时区（**跟 IP 所在地一致**）、屏幕分辨率、CPU 核数、内存 |
| 渲染指纹 | Canvas、WebGL（厂商 / 渲染器）、AudioContext、字体列表、ClientRects —— 加稳定噪声，同一环境每次一样 |
| 网络 | WebRTC（禁用或替换为代理 IP）、DNS 走代理、不泄露本机 IP |
| 行为 | 键鼠节奏、打字速度（自动化任务时模拟） |

原则：**一致性比随机更重要**。时区、语言、IP 国家、UA 系统必须相互对得上；同一个账号的指纹一旦确定就不要变。

## 5. IP 封装（代理）

- **每个账号绑定一个固定出口 IP**，不和别的账号共用；IP 所在国家尽量和账号注册地 / 常用地一致。
- 类型优先级：**静态住宅 IP / ISP IP**（最像真人）＞ 动态住宅（会话保持）＞ 机房 IP（社媒几乎必被识别，只适合抓公开页）。
- 协议：SOCKS5 / HTTP，带账号密码；CRM 里统一管理代理池（供应商、到期时间、国家、绑定了哪个账号）。
- 健康检查：定时检测连通性、出口 IP 是否变化、是否进了黑名单（如 IP 欺诈分），异常时提醒，**不自动换 IP**（换 IP 本身就是风控信号），由管理员确认后再换。
- 国内团队访问海外平台：代理供应商要选能从国内稳定直连的，或者客户端先走企业自己的出海专线。

## 6. CRM 侧功能（社媒矩阵模块）

1. **账号库**：平台、账号名、登录邮箱/手机（加密存储，沿用现有 `src/server/crypto.ts`）、二次验证方式、所属人、状态（正常 / 受限 / 封禁）、绑定环境和 IP。
2. **环境分配与权限**：账号分配给某个员工或部门；员工只能启动分配给自己的环境；主管可以收回。**密码不对员工明文展示**，只能通过环境一键登录。
3. **启动环境**：CRM 里点「打开」→ 调指纹浏览器 API 启动对应 Profile（路线①），或打开云端浏览器窗口（路线③）。
4. **操作审计**：谁在什么时间打开了哪个账号、用了多久；离职交接时一键转移全部账号。
5. **消息回流**（第二阶段）：在环境里读取 LinkedIn / Messenger / Instagram 私信，按对方主页链接匹配到 CRM 的客户社媒（本期的 `CustomerSocial`），写进客户跟进时间线，和邮件、WhatsApp 并列。
6. **客户动态抓取**（第二阶段）：用云端只读环境，登录一个「观察号」，按跟踪名单定期看重点客户的 LinkedIn / Instagram 更新，写入本期已有的 `SocialPost`，在「社媒动态」里展示。
7. **发布排期**（第三阶段，可选）：一个内容同时发到多个账号，按账号所在时区排期。

数据模型（草拟）：

```
SocialAccount   社媒账号（平台、账号名、加密凭据、负责人、状态、环境 id、代理 id）
BrowserProfile  浏览器环境（厂商、外部 profile id、指纹参数快照、最近启动时间）
ProxyEndpoint   代理（协议、主机、端口、加密的账号密码、国家、类型、到期、健康状态）
SocialSession   启动 / 关闭记录（谁、哪个账号、开始、结束、来源 IP）
```

## 7. 合规与风险提示（请务必看）

- 多账号管理本身在各平台条款里都是灰色地带：**LinkedIn 明确禁止自动化抓取和虚假账号**，Meta 对批量账号同样严格。指纹浏览器能降低关联风险，但不能保证不封号。
- 建议产品定位为「**团队账号安全托管 + 人工操作**」，自动化只做只读、低频的事情（看动态、同步消息），**不做批量加好友、群发私信这类高风险自动化**。
- 抓取客户动态只读公开或观察号可见的内容，遵守各平台 robots / 频率限制；涉及欧盟客户的个人数据要考虑 GDPR（记录来源、可删除）。
- 凭据安全：账号密码、代理密码、Cookie 全部加密存储；云端环境的数据盘按租户隔离。
